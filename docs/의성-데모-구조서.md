# 의성 데모 구조서: 입력 → 확산 예측 → 규칙 판정 → LLM 대응 생성 → 출력

2025-03-22 의성 산불을 상황도 화선 보고 4번(12:50 · 13:10 · 13:45 · 14:20)마다 다시 돌려 대응 제안서를 만드는
데모의 코드 · 데이터 구조를 개발자가 따라가며 디버깅할 수 있게 정리한 문서다(2026-11-08, 브랜치 `feat/agent-demo`).

**설계 원칙(11/8 사용자 결정):** 규칙 엔진은 규칙으로 판단할 수 있는 것만 판정해 넘긴다.
무엇을 할지(대응 제안)는 LLM(EXAONE 4.5 33B, 11/9까지는 4.0 32B)이 표준매뉴얼 · 법령을 검색(RAG)해 그 근거로 쓴다.
코드가 문장을 미리 정해 두는 고정문 · 문단 자리는 없다.

```

        ▼
[2 규칙 판정]  demo/uiseong/step2_rules.py  →  rules/ (규칙 엔진, 황승준 담당 · 고치지 않음)
  rules.Inputs → build_context → bundles 16묶음 → items 12개 → build_llm_input
        │  llm_input = {bundles, common, items}                     → round_k/02_rules/
        ▼
[3 LLM 대응 생성]  demo/uiseong/step3_agent.py  →  agent/ (항목마다, 4개 동시)
  situation.py  bundles → 상황 깃발(불이 큼 · 작음 · 단계 오름 · 지휘권 바뀜 · 밤 · 도지사 …, 회차에 한 번)
  guides.py     항목별 작성 지침: 깃발에 따라 켜지는 줄(쓸 것 · 덧붙일 제안 · 쓰지 않을 것 · 검색 질의)

  clients.py    vLLM(EXAONE) 호출, json_schema로 출력 묶음(evidence는 준 청크 ID만)
  check.py      quote(근거 문장) · 판정 값 · 근거 · 권한 · 형식 검사 → 실패하면 1회 다시 → 그래도 실패한 제안만 뺌
  cite.py       evidence 청크 ID → 근거 표기 [p.79, 시행령 제21조①·②]
  generate.py   위 순서를 묶고 조립(제안 + 판정 자료)                           → round_k/04_llm/ · 05_output/
        ▼
[4 출력]  runs/<이름>/round_k.json · summary.json · run.log
  build_viewer.py → viewer.html(지도 · 제안서 · 예측 검증 · 실행 기록)
  verify.py       → 검증_보고.md(근거 뒷받침 · 시나리오 v3 목표 대비 · 백서 실제 기록 대비)
```

GPU 서버(A6000)에서 도는 것: ELMFIRE(CPU) · 근거 서버(KURE-v1 임베딩 GPU + FAISS + PostgreSQL) ·
vLLM(EXAONE, GPU 0). 규칙 엔진 · 검사 · 조립은 순수 파이썬이라 어디서나 돈다.

## 4. 단계별 상세

### 0. 입력 — `rounds.py` · `data.py`

| 무엇 | 함수 | 결과 |
|---|---|---|
| 회차 · 현장 보고 | `rounds.load(input)` | `Scenario(title, incident, rounds[Round], ignition_t_s)`. `Round.t_s` = ELMFIRE 시각(기상 밴드 1 = 11:00 뒤 초) |
| 지도 자료 | `data.MapData(input)` | 마을 · 주택 · 대피소 · 취약시설 · 국가유산 · 송전선 · 도로 · 경찰 · 소방 · 병원 · 헬기 기지 · 인접 시군 · 화선(`report(at)`) |

### 1. 확산 예측 — `step1_spread.py` · `spread/perimeter_run.py`

| 순서 | 함수 | 하는 일 |
|---|---|---|
| 1 | `calibrate_round(deck, work, md, rd, sc, method)` | 배율 ① k−1보 → k보 면적 맞춤 ② k보 + 발화 뒤 평균 성장 1시간(1회차는 ②만) → 기하평균. 각 배율은 `perimeter_run.calibrate`(log adj 이분 탐색, 2 ~ 14번 ELMFIRE) |
| 2 | `perimeter_run.run(deck, dir, t, 8, observed, adj)` | 실행 폴더(phi = 관측 화선 −1/+1, adj = 덱 adj × 배율, namelist 시간 창) → ELMFIRE → 도달 시간 래스터 |
| 3 | `perimeter_run.ranges(res, observed)` | P0 = 관측 화선, Pn = P0 ∪ 도달 ≤ t0+n시간(구멍 메움 · 겹) |
| 4 | `validate(md, rd, observed, res)` | 8시간 안 뒤 상황도 화선과 면적 · IoU(제안에는 쓰지 않음) |
| 5 | `save` / `load` | `01_spread/spread.json`(EPSG:5179 WKT 포함) — `--reuse-spread`가 읽는다 |

### 2. 규칙 판정 — `step2_rules.py` · `rules/`

`make_inputs`가 `rules.Inputs`를 채운다(범위 P0~P8, 0시 바람 = 상황 보고, 1~8시간 바람 = ELMFIRE 기상 `wind_series`,
지도 자료, 투입 자원, 마을별 현장 입력, 직전 회차 단계 · 경보). `build_llm_input`(rules/llm_input.py)이 돌려주는 것:

| 칸 | 내용 |
|---|---|
| `bundles` | 판정 묶음 16개: time · area · stage · commander · villages · vulnerable · protected · houses · shelters · roads · alerts · mobilization · resources · weather · spread · agencies |
| `common` | reader · incident · proposal(버전 · 기준 화선) · current_stage · commander |
| `items[]` | S1~S6 · E1~E6. 칸: `finding` · `facts` · `withheld` · `do_not_state` · `rule_basis` · `sections[].blocks[]`(action · list · table · note · fixed) · `anchor_basis` · `targets` · `status` |

### 3. LLM 대응 생성 — `step3_agent.py` · `agent/`

`step3_agent.with_situation(llm_input)`이 회차마다 상황 깃발을 한 번 만들어 `common["situation"]`에 넣고,
`Agent._one(common, item, prev)`가 항목 하나를 이 순서로 처리한다(`agent/generate.py`).

| 순서 | 모듈 · 함수 | 입력 → 출력 | 볼 곳 |
|---|---|---|---|
| ⓪ 상황 · 지침 | `situation.flags(bundles, items, common)` · `guides.render` · `extra_topics` · `queries` | 깃발 = large_now(지금 100 ha 이상) · large_soon(8시간 안에 넘음, large_at) · small · escalation(5시간 뒤 단계 오름) · stage_up_from_prev · commander_change · reader_upper(도지사 등) · now_is_night · sunset_in_range · night_arrival(밤에 닿는 마을) · wind_rising · evac_unconfirmed · vulnerable_* · power_lines · heritage · roads_at_risk · shelters_* · other_sigungu · alerts_changed/removed. 항목마다 `GUIDES[id]`의 줄 중 `when`이 참인 것만 켠다. kind: do(쓸 것) · extra(덧붙일 제안 — 그 주제를 고를 수 있게 됨) · avoid(쓰지 않을 것). 줄의 `q`는 검색 질의로 더한다 | `04_llm/<항목>.json`의 `guide` · `extras` |
| ① 판정 · 주제 고르기 | `judgment.judgment_of(item)` · `topics_of` | 규칙 엔진 항목 → `{id, name, finding, facts, withheld, do_not_state, data, topics}`. `topics` = 다룰 주제(action의 소제목 · 주제 · 쓸 판정 값 이름 — 판정에 따라 달라짐). action의 anchors(주제별 근거 쪽) · anchor_basis · fixed 문장 · status는 **넘기지 않는다**. `data` = list · table · note를 글줄로 | `04_llm/<항목>_prompt.txt`의 [다룰 주제] · [규칙 엔진 판정] |
| ①-2 상황 문장 | `situate.sentences(item, topics)` | 판정 값이 들어가는 주제의 상황 문장을 facts로 조립: S1 현재 기준 단계(기준별 값 · 단계, 직전 회차 대비) · 5시간 뒤 단계(`first_over` 시각 · 면적) · 지휘권자, S2 주택 보호 배치(마을별 최소 동수) · 송전시설 보호(구간 · 닿는 시각 · 5/8시간 길이) · 문화유산 이동 · 경비, S3 투입 자원(기관별 수) · 현재/5시간 뒤 동원 범위(고시 별표 판정). 조사(이/가 · 으로/로)는 끝 글자 받침으로 고른다. 만들 수 없으면 그 주제는 LLM이 전부 쓴다 | `04_llm/<항목>.json`의 `situations` |
| ② 근거 검색 | `retrieve.retrieve(evidence, item, judgment, common, scope, k=10, guide_queries)` | 판정 근거 = `rule_basis` + S6 · E6 요청 표의 「근거」 칸(p.95 · 고시 별표). 쪽 ID(`SM-p078`)는 그 쪽의 조각(`SM-p078-s01 …`)으로 펼쳐 `/fetch`. 검색 = 질의 ① 항목 범위(`prompt.ITEM_SCOPE`) ② 이름 + finding ③ 범위 + 상황(밤 · 단계 · 읽는 사람) ④ 다룰 주제마다 「이름 + 소제목 + 주제」 → `/search` 상위 5개씩 합쳐 점수순 10개. 켜진 지침 질의는 점수에 밀려도 질의마다 상위 2개를 더 넣는다 | `03_rag/<항목>.json`(질의 · 지침 질의 · 판정 근거 ID · 찾은 청크 · 점수) |
| ③ 메시지 | `prompt.messages(common, judgment, chunks, names, guide, situation_line, situations, action_only)` | system(`SYSTEM`, 11번 = 상황 문장이 붙는 주제는 할 일 문장만) + user([항목 범위] · [다른 항목] · [읽는 사람의 권한] · [읽는 사람 · 상황](+ 「이번 상황: 규모 · 단계 · 지휘권자 · 시간대 · 바람」 한 줄) · [규칙 엔진 판정] · [다룰 주제](상황 문장이 있으면 그 주제 아래 「상황 문장(제안 앞에 그대로 붙음)」 — 그 주제의 문단 꼴 예시는 할 일 문장만) · [이 항목 작성 지침] · [문단 꼴 예시: 같은 항목의 v3 목표 문단, 숫자 · 시각 · 이름을 N · HH:MM · ○○로 가림] · [판정 자료] · [근거 발췌]) | `04_llm/<항목>_prompt.txt` |
| ④ 호출 | `clients.LLM.chat(msgs, schema=prompt.schema(ids, topics, extras))` | vLLM `/v1/chat/completions`, temperature 0.2(다시 쓰기 0.5), 추론 모드 끔, `response_format` json_schema: `{"proposals": [{topic, category, text, evidence[ID enum], quote}]}`. topic은 다룰 주제 + 이번에 켜진 덧붙일 주제 중에서만, 개수는 다룰 주제 수 ~ 다룰 주제 + 덧붙일 주제 수(지침을 쓰면 「그 밖의 제안」 칸은 없음). quote = 근거 발췌에서 조치를 적은 문장을 옮긴 것 | `04_llm/<항목>.json`의 `attempts[].raw` |

| ⑦ 조립 | `generate.assemble` · `cite.render` | 시나리오 v3 배치: 규칙 엔진 섹션마다 [소제목 → 그 주제의 제안 문단(끝에 근거 표기, see가 있으면 「세부 내용은 S6 참조.」) → 그 섹션의 목록 · 표 · ※]. 덧붙일 주제의 제안은 그 주제 이름을 소제목으로 뒤에 붙인다. 주제가 없는 항목(E6)은 제안을 먼저. 상황 문장이 있으면 문단 = 상황 문장(코드) + 할 일 문장(LLM)이고 블록에 `situation` · `action_text` · `source: "rule+llm"`을 남긴다. 문단 블록에 `body`(근거 표기 없는 본문) · `cite`(표기)를 따로 둔다 — 화면은 본문만 보이고 근거는 마우스를 올리면. `evidence`(인용 청크 원문) | `05_output/proposal.json` |

상태: `ok`(모두 통과) · `partial`(일부 뺌) · `failed`(통과한 제안 없음 — 화면에 그 사실만) · `reused`(판정 · 상황이 직전 회차와 같아 다시 씀).

## 9. 설계 결정과 한계

- **판정 / 생성 경계:** 규칙 엔진 출력 중 판정(`finding` · `facts` · `withheld` · 목록 · 표 · ※)만 LLM에 준다. 규칙 엔진이 미리 정한 문단 자리 ·
  주제 · 근거 쪽과 고정 문장은 쓰지 않는다. 규칙 엔진 코드는 그대로 두고 에이전트 쪽에서 고른다.
- **판정 근거(`rule_basis`)는 가져온다:** 그 판정(단계 · 구역 · 동원 범위)을 정한 법령 · 매뉴얼이라 판정을 설명하는 근거다.
  조치는 검색 근거와 판정 근거 어디서든 고를 수 있고, `03_rag`의 `origin`으로 구분된다.
- **다룰 주제와 문단 꼴 예시(11/8 저녁 사용자 결정):** 처음 재설계(주제 · 예시 없음)에서는 문단이 한 줄씩(회차 1 합계 1,255자, v3 목표 2,447자)이고 S4가 주제에서 빗나갔다. 그래서 규칙 엔진 항목의 다룰 주제(소제목 · 주제)와 같은 항목의 v3 목표 문단을 값을 가린 꼴로 넘긴다. 문장 내용 · 근거는 여전히 LLM이 근거 검색으로 정한다. 회차 1은 예시와 겹치므로 회차 2 ~ 4를 주 검증으로 본다
- **항목별 작성 지침(11/8 밤 사용자 결정):** 산불 대응 과정은 회차 · 산불마다 거의 같으므로 S1 ~ E6마다 「불이 크면 · 작으면 ·
  단계가 오르면 · 밤이면 · 읽는 사람이 도지사면」 쓸 것 · 덧붙일 제안 · 쓰지 않을 것을 `guides.py`에 적어 두고, 회차의 상황 깃발로
  켠다. 지침에는 판정 값을 적지 않고, 지침의 조치도 근거 발췌에 있을 때만 쓴다. 덧붙일 제안(예: 대형산불 → 「통합지휘본부 운영」)은
  켜질 때만 json_schema의 topic으로 열리므로 상황에 따라 나오기도 하고 안 나오기도 한다. 의성 4회차는 모두 「8시간 안에 대형산불」이
  거나 대형산불이라 「작은 불」 줄은 테스트(`test_agent_guides.py`)로만 확인했다. 의성 회차에 맞춘 지침이라 과적합 위험이 있다
- **판정 값 상황 문장은 코드가 조립(11/8 밤 사용자 결정):** tune11에서 LLM이 판정 값을 근거 원문의 기준값으로 바꿔 썼다(1단계 지상 범위
  「경상북도 100%」 · 「최소 20동」 · 「세 기준 모두」). 검사는 숫자가 근거 원문에 있으면 통과시키므로 못 잡는다. 그래서 값이 대부분인
  S1 · S2 · S3 주제는 상황 문장을 `situate.py`가 facts 그대로 쓰고, LLM은 그 뒤의 할 일 문장만 근거 검색으로 쓴다(할 일 문장에 상황 문장에
  없는 숫자를 쓰면 검사에 걸림). 무엇을 할지는 여전히 LLM + RAG가 정한다. 규칙 엔진 facts 구조가 바뀌면 `situate.py`와
  `tests/unit/test_agent_situate.py`를 함께 고친다. 상황 문장을 규칙 엔진 쪽(고정 문장 칸)으로 옮길지는 규칙 엔진 담당과 정할 일이다.
  S4 · E2 · E4 도로 · E5 지역은 다음 차례 후보
- **화면은 제안 문장만:** 근거 표기 · 근거 문장 · 원문 발췌는 문단에 마우스를 올리면(누르면 고정) 보인다(`viewer_template.html`).
  화면용 블록의 `body` · `cite`를 따로 두어 다른 화면(wfg-client)도 같은 방식으로 그릴 수 있다. 상황 문장이 붙은 문단은 마우스를 올리면
  「판정 값 문장(코드)」과 「할 일 문장(LLM)」을 나눠 보인다
- **근거 없는 제안은 보이지 않는다:** evidence는 그 호출에 준 청크 ID만 고를 수 있고(json_schema enum), 비면 검사에서 빠진다.
- **S6 · E6 요청 표, E4 대피소 후보는 규칙 엔진 출력이다:** 판정 자료로 보여 주고 LLM은 그것을 바탕으로 제안한다.
  표의 「요청 사항」 칸도 LLM으로 옮길지는 규칙 엔진 담당과 정할 일이다.
- **판정 모델:** 검증의 근거 뒷받침 · 목표 대비 판정도 같은 EXAONE이 한다(후하게 볼 수 있다).
- **자료 공백:** 전통사찰 · 고속도로 나들목 자료 없음, 헬기 기지 관할은 가정값, 의성 밖은 읍면 단위.
