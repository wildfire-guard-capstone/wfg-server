# 의성 데모 구조서: 입력 → 확산 예측 → 규칙 판정 → LLM 대응 생성 → 출력

2025-03-22 의성 산불을 상황도 화선 보고 4번(12:50 · 13:10 · 13:45 · 14:20)마다 다시 돌려 대응 제안서를 만드는
데모의 코드 · 데이터 구조를 개발자가 따라가며 디버깅할 수 있게 정리한 문서다(2026-11-08, 브랜치 `feat/agent-demo`).

**설계 원칙(11/8 사용자 결정):** 규칙 엔진은 규칙으로 판단할 수 있는 것만 판정해 넘긴다.
무엇을 할지(대응 제안)는 LLM(EXAONE 4.0 32B)이 표준매뉴얼 · 법령을 검색(RAG)해 그 근거로 쓴다.
코드가 문장을 미리 정해 두는 고정문 · 문단 자리는 없다.

## 4. 단계별 상세

### 0. 입력 — `rounds.py` · `data.py`

| 무엇 | 함수 | 결과 |
|---|---|---|
| 회차 · 현장 보고 | `rounds.load(input)` | `Scenario(title, incident, rounds[Round], ignition_t_s)`. `Round.t_s` = ELMFIRE 시각(기상 밴드 1 = 11:00 뒤 초) |
| 지도 자료 | `data.MapData(input)` | 마을 · 주택 · 대피소 · 취약시설 · 국가유산 · 송전선 · 도로 · 경찰 · 소방 · 병원 · 헬기 기지 · 인접 시군 · 화선(`report(at)`) |

### 1. 확산 예측 — `step1_spread.py` · `spread/perimeter_run.py`

| 순서 | 함수 | 하는 일 |
|---|---|---|
| 1 | `calibrate_round(deck, work, md, rd, sc, method)` | 배율 ① k−1보 → k보 면적 맞춤 ② k보 + 발화 뒤 평균 성장 1시간(1회차는 ②만) → 기하평균. 각 배율은 `perimeter_run.calibrate`(log adj 이분 탐색, 2 ~ 14번 ELMFIRE) |
| 2 | `perimeter_run.run(deck, dir, t, 8, observed, adj)` | 실행 폴더(phi = 관측 화선 −1/+1, adj = 덱 adj × 배율, namelist 시간 창) → ELMFIRE → 도달 시간 래스터 |
| 3 | `perimeter_run.ranges(res, observed)` | P0 = 관측 화선, Pn = P0 ∪ 도달 ≤ t0+n시간(구멍 메움 · 겹) |
| 4 | `validate(md, rd, observed, res)` | 8시간 안 뒤 상황도 화선과 면적 · IoU(제안에는 쓰지 않음) |
| 5 | `save` / `load` | `01_spread/spread.json`(EPSG:5179 WKT 포함) — `--reuse-spread`가 읽는다 |

### 2. 규칙 판정 — `step2_rules.py` · `rules/`

`make_inputs`가 `rules.Inputs`를 채운다(범위 P0~P8, 0시 바람 = 상황 보고, 1~8시간 바람 = ELMFIRE 기상 `wind_series`,
지도 자료, 투입 자원, 마을별 현장 입력, 직전 회차 단계 · 경보). `build_llm_input`(rules/llm_input.py)이 돌려주는 것:

| 칸 | 내용 |
|---|---|
| `bundles` | 판정 묶음 16개: time · area · stage · commander · villages · vulnerable · protected · houses · shelters · roads · alerts · mobilization · resources · weather · spread · agencies |
| `common` | reader · incident · proposal(버전 · 기준 화선) · current_stage · commander |
| `items[]` | S1~S6 · E1~E6. 칸: `finding` · `facts` · `withheld` · `do_not_state` · `rule_basis` · `sections[].blocks[]`(action · list · table · note · fixed) · `anchor_basis` · `targets` · `status` |

### 3. LLM 대응 생성 — `step3_agent.py` · `agent/`

`Agent._one(common, item, prev)`가 항목 하나를 이 순서로 처리한다(`agent/generate.py`).

| 순서 | 모듈 · 함수 | 입력 → 출력 | 볼 곳 |
|---|---|---|---|
| ① 판정 · 주제 고르기 | `judgment.judgment_of(item)` · `topics_of` | 규칙 엔진 항목 → `{id, name, finding, facts, withheld, do_not_state, data, topics}`. `topics` = 다룰 주제(action의 소제목 · 주제 · 쓸 판정 값 이름 — 판정에 따라 달라짐). action의 anchors(주제별 근거 쪽) · anchor_basis · fixed 문장 · status는 **넘기지 않는다**. `data` = list · table · note를 글줄로 | `04_llm/<항목>_prompt.txt`의 [다룰 주제] · [규칙 엔진 판정] |
| ② 근거 검색 | `retrieve.retrieve(evidence, item, judgment, common, scope, k=8)` | 판정 근거 = `rule_basis` + S6 · E6 요청 표의 「근거」 칸(p.95 · 고시 별표). 쪽 ID(`SM-p078`)는 그 쪽의 조각(`SM-p078-s01 …`)으로 펼쳐 `/fetch`. 검색 = 질의 ① 항목 범위(`prompt.ITEM_SCOPE`) ② 이름 + finding ③ 범위 + 상황(밤 · 단계 · 읽는 사람) → `/search` 상위 6개씩 합쳐 점수순 8개 | `03_rag/<항목>.json`(질의 · 판정 근거 ID · 찾은 청크 · 점수) |
| ③ 메시지 | `prompt.messages(common, judgment, chunks, names)` | system(`SYSTEM`) + user([항목 범위] · [다른 항목] · [읽는 사람의 권한] · [읽는 사람 · 상황] · [규칙 엔진 판정] · [다룰 주제] · [문단 꼴 예시: 같은 항목의 v3 목표 문단, 숫자 · 시각 · 이름을 N · HH:MM · ○○로 가림] · [판정 자료] · [근거 발췌]) | `04_llm/<항목>_prompt.txt` |
| ④ 호출 | `clients.LLM.chat(msgs, schema=prompt.schema(ids))` | vLLM `/v1/chat/completions`, temperature 0.2(다시 쓰기 0.5), 추론 모드 끔, `response_format` json_schema: `{"proposals": [{category, text, evidence[ID enum], quote}]}` 1~5개. quote = 근거 발췌에서 조치를 적은 문장을 옮긴 것 | `04_llm/<항목>.json`의 `attempts[].raw` |
| ⑤ 검사 | `check.tidy` · `strip_subject` · `fix_category` · `generate.fix_evidence` · `check.check(...)` | 표기 정리(괄호 지움 · 「의성군수는」 주어 지움) → quote가 다른 청크에서 왔으면 evidence를 그 청크로 바로잡음 → 검사: 근거 없음 · 다룰 주제마다 제안 있음 · 판정에 없는 숫자/시각/수사/단계/이름 · 입력 설명 옮김 · 할 일 부정 · 읽는 사람 자신에게 지시 · 「~하십시오」 없음 · 방법 빠진 말 · 4문장 · 450자 · 권한(도지사 → 군수에게 지시) · 「최소 N동」 · 「등」 · 항목 금칙 · 반복 · 대상만 바꿔 나눈 제안. quote가 근거에서 왔는지(네 글자 조각 70%)는 **기록만**(`quote_ok`, 근거 뒷받침은 verify.py) | `attempts[].errors` · `evidence_fixed` |
| ⑥ 다시 쓰기 | `prompt.retry_message(errors, proposals)` | 문제 목록 + 직전 제안 → 최대 2회 더(시도 3번). 통과한 제안이 가장 많은 시도를 쓰고 끝까지 걸린 제안은 `dropped`(이벤트 로그 「근거 부족」) | `04_llm/<항목>.json`의 `dropped` |
| ⑦ 조립 | `generate.assemble` · `cite.render` | 시나리오 v3 배치: 규칙 엔진 섹션마다 [소제목 → 그 주제의 제안 문단(끝에 근거 표기, see가 있으면 「세부 내용은 S6 참조.」) → 그 섹션의 목록 · 표 · ※]. 주제가 없는 항목(E6)은 제안을 먼저. `evidence`(인용 청크 원문) | `05_output/proposal.json` |

상태: `ok`(모두 통과) · `partial`(일부 뺌) · `failed`(통과한 제안 없음 — 화면에 그 사실만) · `reused`(판정 · 상황이 직전 회차와 같아 다시 씀).

### 4. 출력

llm_calls(토큰 · 시간) · timing. 뷰어는 이것만 읽는다.

## 6. 데이터 형식

**LLM 출력(json_schema로 강제):**
```json
{"proposals": [{"category": "즉시|대기|협의|요청", "text": "…하십시오.", "evidence": ["SM-p079-s02", "REG-ROLE-a8"], "quote": "<근거 발췌에서 조치를 적은 문장>"}]}
```
**화면용 항목(`05_output/proposal.json`):**
```json
{"id": "E2", "name": "대피 대상·순서·시점", "state": "ok", "finding": "…", "withheld": [...],
 "sections": [{"title": "대응 제안", "blocks": [{"type": "paragraph", "category": "즉시", "text": "… [p.75·79].", "evidence": ["SM-p075", "SM-p079-s01"], "source": "llm"}]},
              {"title": "판정 자료(규칙 엔진)", "blocks": [{"type": "list", "rows": [...]}, {"type": "note", "text": "※ …"}]}],
 "evidence": [{"chunk_id", "label", "doc_name", "section", "page", "origin", "text"}]}
```
**근거 청크 ID와 표기(`agent/cite.py`):** `SM-p079-s02` → p.79 · `SM-p079`(쪽 전체, 검색 제외) → p.79 ·
`DEC-FDPA-a21-h01-02` → 시행령 제21조①·② · `REG-ROLE-t3-p2` → 규정 별표 3 · `NOTI-MOBL-t0-p1` → 고시 별표.

## 7. RAG 구성

## 9. 설계 결정과 한계

- **판정 / 생성 경계:** 규칙 엔진 출력 중 판정(`finding` · `facts` · `withheld` · 목록 · 표 · ※)만 LLM에 준다. 규칙 엔진이 미리 정한 문단 자리 ·
  주제 · 근거 쪽과 고정 문장은 쓰지 않는다. 규칙 엔진 코드는 그대로 두고 에이전트 쪽에서 고른다.
- **판정 근거(`rule_basis`)는 가져온다:** 그 판정(단계 · 구역 · 동원 범위)을 정한 법령 · 매뉴얼이라 판정을 설명하는 근거다.
  조치는 검색 근거와 판정 근거 어디서든 고를 수 있고, `03_rag`의 `origin`으로 구분된다.
- **다룰 주제와 문단 꼴 예시(11/8 저녁 사용자 결정):** 처음 재설계(주제 · 예시 없음)에서는 문단이 한 줄씩(회차 1 합계 1,255자, v3 목표 2,447자)이고 S4가 주제에서 빗나갔다. 그래서 규칙 엔진 항목의 다룰 주제(소제목 · 주제)와 같은 항목의 v3 목표 문단을 값을 가린 꼴로 넘긴다. 문장 내용 · 근거는 여전히 LLM이 근거 검색으로 정한다. 회차 1은 예시와 겹치므로 회차 2 ~ 4를 주 검증으로 본다
- **근거 없는 제안은 보이지 않는다:** evidence는 그 호출에 준 청크 ID만 고를 수 있고(json_schema enum), 비면 검사에서 빠진다.
- **S6 · E6 요청 표, E4 대피소 후보는 규칙 엔진 출력이다:** 판정 자료로 보여 주고 LLM은 그것을 바탕으로 제안한다.
  표의 「요청 사항」 칸도 LLM으로 옮길지는 규칙 엔진 담당과 정할 일이다.
- **판정 모델:** 검증의 근거 뒷받침 · 목표 대비 판정도 같은 EXAONE이 한다(후하게 볼 수 있다).
- **자료 공백:** 전통사찰 · 고속도로 나들목 자료 없음, 헬기 기지 관할은 가정값, 의성 밖은 읍면 단위.
